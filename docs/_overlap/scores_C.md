## Ambiguities I resolved

1. **The convention names eight `prevention` values but does not define them.**
   Section 2 says "grade by v1.2's eight definitions", and v1.2 is not in the
   instrument file. I did not go looking for it. I derived working definitions
   from the value names plus what section 2 does state: GATE-EXISTING = a
   standing check existed that could have seen this unrewritten; GATE-ABSENT =
   none existed, or an existing one would have needed rewriting; GATE-FIRED-
   IGNORED / GATE-FIRED-CAUGHT = a standing check produced a signal that was
   ignored, or that caught it; CONTRACT = a stated rule whose observance would
   have prevented it; CONTRACT-MISFIRED = a stated rule was applied and was
   itself wrong or out of its validity; PROXY-MEASURE = a stand-in quantity was
   taken for the target quantity; ADVERSARY = only a reader with a lens could
   have caught it. Every figure here is conditional on those derivations.

2. **The strict standing-check reading nearly collapses ADVERSARY into
   GATE-ABSENT, which would make almost every row a SPLIT.** Section 8 says an
   implausibly high SPLIT count is evidence against the convention, so I read
   that as instruction not to let the collapse happen mechanically. My line:
   where the defect is a discrete checkable datum (a count, a path, a line
   range, a symbol's presence) it is gate-shaped, so GATE-ABSENT; where the
   defect is a reasoning error, a mischaracterisation or an over-broad
   statement that no instrument could fire on, ADVERSARY. This is the single
   largest judgement call in my scoring and a different scorer could reasonably
   put the line elsewhere.

3. **"Record the SET of values that co-apply" does not say whether a single
   value is a legal set.** I took a set of one as legal and assigned multiple
   values only where two had independent grounds in the row's own text, rather
   than listing every value that could be argued. Two rows came out multi-value.

4. **Whether a mechanised run counts as a standing check when it is not a
   pre-existing named guard.** Section 2 admits "the test suite" and "a named
   guard" but excludes verifier and adversarial passes. I ruled that a test or
   tool RUN producing a pass/fail signal is GATE-FIRED-CAUGHT even when the
   test was written in the same session (chunk1-31, chunk2-29, chunk2-33),
   because the firing verb and the signal are both present. I ruled that a
   "gate" staffed by a reader (chunk2-04's second read-only gate, chunk1-11's
   adversarial gate) is not, per section 2's explicit exclusion. chunk4-04's
   "baselining check" is the borderline case and I admitted it.

5. **FRESH carries no sub-value, so an over-generalisation produced in-session
   is not expressible.** Section 3's state test made chunk4-20 and chunk1-51
   FRESH even though their defect shape is OVER-GENERALISED. I followed the
   state test and recorded the loss in the row notes rather than bending
   origin_time to fit the shape.

6. **A dispatch, directive or override written in-session.** Section 3's
   declared boundary covers an in-session subagent report but not a directive
   handed down to a slice. I treated both the same way - uncommitted at the
   moment of refutation, therefore FRESH (chunk3-07, chunk3-41) - while a
   directive already committed as a tracked artifact is INHERITED (chunk3-04,
   chunk4-07).

7. **`fix_chain` forward links across rows in the same sample.** Section 4's
   floor rule says score down where the record does not establish a link. I
   counted a link only where the row's own text names the later refutation
   (chunk1-24, chunk1-27) or where another row in this same sample names this
   row's remedy as refuted (chunk2-23, whose remedy of 91 chunk4-34 calls
   stale). Everything else is 0 as a floor, not as a finding.

8. **DECAYED versus BORN-WRONG where the row does not time-index the falsity.**
   I defaulted to BORN-WRONG unless the row's own wording carries a time index
   ("AT HEAD", "pre-existing stale prose", "already content-stale", "now
   stale") or the mechanism of decay is visible in the text (a directory
   growing, a file growing, work shipping after the claim). chunk4-10 and
   chunk1-47 were the closest calls and are noted at the row.
